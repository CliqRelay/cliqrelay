# Handoff: gate the extension side panel behind sign-in

## Context

The CliqRelay browser extension opens straight onto the capture page. There is no
auth gate anywhere, so a signed-out user sees a fully enabled "start capturing"
button that cannot possibly work.

What actually happens today when a signed-out user hits record
(traced through `oss/apps/extension/src`):

1. `handleStart` → `bridge.startRecording()` → background `session-manager.ts`.
2. `handleSidePanelCommand` fires `offscreenManager.startSession(...)` with a bare
   `void` — nothing is awaited, no API call happens yet. The state machine flips
   to `recording` and the UI shows a live session. **The user believes it worked.**
3. On the first captured click, `getOrCreateGuideId()` calls
   `api.guides.createGuide({ teamId: "" }, await withCsrf())` with no session and
   no CSRF token. The API returns 401/403.
4. `queue.service.ts` retries that guaranteed-401 request with exponential backoff
   up to `UPLOAD_MAX_ATTEMPTS`, then surfaces a raw API error string as a failed
   step chip — not "you're signed out".

The goal: when there is no session, the side panel shows a sign-in screen instead
of the capture UI, and the record path can no longer be reached in that state.

monorepo root; drop the `oss/` prefix once you are in the OSS repo.

| Router (`createHashHistory`, no context type)        | `.../sidepanel/router.tsx`                              |

| The one existing signed-out signal                   | `.../sidepanel/hooks/useRecentGuides.ts`                |
| Background guide creation that 401s                  | `.../src/background/session-manager.ts`                 |
| Retry queue that hammers the 401                     | `.../src/services/offscreen/queue.service.ts`           |

Auth model: cookie-based against the Go API. The session cookie is
`authula.session_token` (HttpOnly, `SameSite=lax`, set in
`oss/apps/api/auth/auth.go`). CSRF is `authula_csrf_token` +
`X-AUTHULA-CSRF-TOKEN`, both already in `COOKIE_CONSTANTS` / `HEADER_CONSTANTS`
in `@repo/data-commons`. The extension reads cookies via
`browser.cookies.get({ url: env.VITE_API_URL })` and sends
`credentials: "include"`. There is **no** auth endpoint in `@repo/api-client` —
auth lives in Authula, which the extension does not talk to at all yet.

The only current signed-out handling is in `useRecentGuides.ts`, which conflates
"no active-team cookie" with "signed out" and renders a dead-end empty state with
no button.

## Design decisions (already agreed — do not relitigate)

1. **Sign-in happens in the web app, not in the extension.** The side panel shows
   a branded screen with a button that opens the web app's `/auth/sign-in` in a
   new tab. The extension then watches for the session cookie and flips itself to
   the capture page.

   Why: the session cookie has to land on the API origin. Posting credentials
   from a `chrome-extension://` page and hoping the cross-origin `Set-Cookie`
   sticks is fragile, and password reset / email verification / OAuth would still
   need the web app. Bonus: web's `routes/__root.tsx` sets the
   `cliqrelay_active_team_id` cookie once the user reaches the dashboard, so this
   flow fixes the missing-team problem for free.

2. **Session truth comes from `authulaClient.core.getMe()`.** Not from cookie
   presence — a stale cookie should read as signed out.

## Implementation

### 1. Env — add the two missing URLs

`oss/apps/extension/src/constants/env.ts` and `.env.local.example`:

```ts
export const env = createEnv({
  clientPrefix: "VITE_",
  client: {
    VITE_API_URL: z.url(),
    VITE_AUTHULA_URL: z.url(),
    VITE_WEB_URL: z.url(),
  },
  runtimeEnv: import.meta.env,
  emptyStringAsUndefined: true,
});
```

Local values mirror the web app: `VITE_AUTHULA_URL=http://localhost:8080/api/auth`
(web's is `${API_URL}/api/auth`), `VITE_WEB_URL=http://localhost:3000`.

Add `"authula": "^0.7.14"` to `oss/apps/extension/package.json` dependencies —
same version the web app pins.

### 2. Authula client for the extension

New: `oss/apps/extension/src/lib/authula-client.ts`.

Model it on `oss/apps/web/src/lib/authula-client-browser.ts`, but with one
critical difference. The SDK falls back to `document.cookie` when no cookie store
is given, and inside a `chrome-extension://` page that is the extension's own
(empty) cookie jar — so `CSRFPlugin` would never find the token. You must pass a
`cookies` factory backed by `browser.cookies`, the same way web passes
`createSsrCookieStore`.

Two contract details verified against `authula@0.7.14`:

- `config.cookies()` is **awaited on every request**, so the factory can be async.
- The returned `CookieStore.getAll()` is **synchronous** and returns
  `{ name, value }[]`. So read the cookies inside the async factory and close over
  the result.

```ts
// src/lib/extension-cookie-store.ts
import type { CookieStore } from "authula";
import { browser } from "wxt/browser";

import { COOKIE_CONSTANTS } from "@repo/data-commons";

import { env } from "@/constants/env";

const READ_COOKIE_NAMES = [COOKIE_CONSTANTS.csrf.name];

export const createExtensionCookieStore = async (): Promise<CookieStore> => {
  const cookies = await Promise.all(
    READ_COOKIE_NAMES.map((name) =>
      browser.cookies.get({ url: env.VITE_API_URL, name }).catch(() => null),
    ),
  );

  const entries = cookies.flatMap((cookie) =>
    cookie?.value ? [{ name: cookie.name, value: cookie.value }] : [],
  );

  // The extension never writes cookies — the API owns them.
  return { getAll: () => entries, set: () => {} };
};
```

The session cookie is HttpOnly and is not read here; it rides along because the
SDK's fetch already sets `credentials: "include"`.

Only `CSRFPlugin` and `CorePlugin` are needed — `getMe` and `signOut` live in
`CorePlugin`. Skip `EmailPasswordPlugin`, `AdminPlugin`, `OrganizationsPlugin`.

> **Check before shipping:** the API's CORS `AllowedOrigins` is built from
> `ClientURL` and `ExtensionURL` (`oss/apps/api/auth/auth.go`). `EXTENSION_URL`
> must be set to `chrome-extension://<id>` or `getMe` will fail CORS. The
> existing `api.guides.*` calls already prove the path works, so this is mostly a
> "confirm it's set in your `.env`" step.

### 3. `useAuthSession` hook

New: `.../sidepanel/hooks/useAuthSession.ts`.

Add `AUTH_SESSION = "auth_session"` to the `QueryKeys` enum in
`src/constants/query-keys.ts` (correct place — Authula is not covered by
`@repo/api-client`, which is exactly what that file's doc comment says it is for).

Export a shared `authSessionQueryOptions` object so both the hook and the route
`beforeLoad` use the same cache entry:

```ts
export const authSessionQueryOptions = {
  queryKey: [QueryKeys.AUTH_SESSION],
  queryFn: () => authulaClient.core.getMe(),
  retry: false, // a 401 is an answer, not a failure to retry
  staleTime: 60_000,
} as const;
```

The hook returns `{ user, isAuthenticated, isLoading, refetch }`.

### 4. Route split — the actual refactor

Give the router a context type so `beforeLoad` can reach the query client. This
mirrors what `oss/apps/web` already does and avoids a flash of capture UI before
the redirect.

- `router.tsx` — accept a `QueryClient`, pass it as router `context`.
- `main.tsx` — create the `QueryClient` once and hand it to `getRouter(queryClient)`.
- `routes/__root.tsx` — `createRootRouteWithContext<{ queryClient: QueryClient }>()`.
  Hide the settings gear when signed out.

New route `routes/sign-in.tsx`:

```ts
export const Route = createFileRoute("/sign-in")({
  beforeLoad: async ({ context }) => {
    try {
      await context.queryClient.ensureQueryData(authSessionQueryOptions);
      throw redirect({ to: "/" }); // already signed in
    } catch (error) {
      if (isRedirect(error)) throw error;
      // not signed in — stay here
    }
  },
  component: SignInPage,
});
```

Existing `routes/index.tsx` — add the mirror guard, keep the body unchanged:

```ts
export const Route = createFileRoute("/")({
  beforeLoad: async ({ context }) => {
    try {
      await context.queryClient.ensureQueryData(authSessionQueryOptions);
    } catch {
      throw redirect({ to: "/sign-in" });
    }
  },
  component: Home,
});
```

Note the `isRedirect` guard in the sign-in route: `throw redirect()` inside a
`try` gets caught by your own `catch`, which is why web's
`oss/apps/web/src/routes/auth/route.tsx` re-throws it. Copy that shape.

Leave `routes/settings/` ungated — it has no user data in it today.

### 5. `SignInView` component

New: `.../sidepanel/components/SignInView.tsx`, exported from the
`components/index.ts` barrel.

- Logo, a short line ("Sign in to CliqRelay to start capturing"), and a primary
  button that calls `browser.tabs.create({ url: \`${env.VITE_WEB_URL}/auth/sign-in\` })`.
- After the click, swap to a quiet "Waiting for sign-in…" state.
- Auto-detect the sign-in: a `useEffect` that registers
  `browser.cookies.onChanged`, and when the changed cookie is the session cookie
  and `removed === false`, invalidates `[QueryKeys.AUTH_SESSION]` and calls
  `router.navigate({ to: "/" })`.
- Keep a manual "I've signed in" button as a fallback — cookie events can be
  missed, and Firefox behaves differently from Chrome here.

Add the session cookie name to `COOKIE_CONSTANTS` in
`oss/packages/data-commons/src/models/constants.ts` rather than hardcoding it:

```ts
session: { name: "authula.session_token" },
```

with a comment noting it mirrors `SessionConfig.CookieName` in
`oss/apps/api/auth/auth.go` (Go can't import the TS constant, so the two have to
be kept in sync by hand).

### 6. Make the background path fail fast when the session dies

The route guard covers "signed out when the panel opens". It does not cover a
session that expires **mid-recording**, which lands you right back in the retry
storm described in Context. Two small changes close it:

- `src/services/offscreen/queue.service.ts` — treat 401/403 as non-retryable.
  `AsyncQueuer`'s `asyncRetryerOptions` retries everything today. Check the error
  status before retrying and fail immediately instead of backing off.
- `src/background/session-manager.ts` — in `getOrCreateGuideId`, catch a 401/403
  from `createGuide`, stop the session rather than leaving the UI showing a live
  recording, and broadcast a state update carrying a signed-out flag so the panel
  can route to `/sign-in`.

`ApiError` (with `.status`) is exported from `@repo/api-client` — that is what
`useRecentGuides.ts` already keys off, so reuse it. Consider extracting
`isUnauthorizedError(error): boolean` into `src/lib/` so the queue, the session
manager, and the hooks all share one definition.

### 7. Clean up the now-redundant signed-out handling

- `useRecentGuides.ts` — the route guard now owns "signed out", so `isSignedOut`
  should stop meaning that. Keep the 401 suppression, but the missing-team branch
  should read as "no team selected", and `RecentGuidesList.tsx`'s empty state
  should say so instead of "Sign in to CliqRelay to see your guides."
- `.../sidepanel/hooks/useGuideSteps.ts` — has no 401 handling at all, so a
  signed-out user with a leftover `activeGuideId` in `browser.storage` gets
  "Failed to load steps. Close and reopen the sidepanel to retry." from
  `StepList.tsx`. Apply the same `isUnauthorizedError` suppression.

### 8. Tests

Vitest runs `src/**/*.test.ts` in the node environment, so no component tests.
Follow the shape of `.../hooks/useRecentGuides.test.ts` — it tests the exported
pure helper (`buildRecentGuidesParams`), not the hook. Extract and test:

- `isUnauthorizedError(error)` — true for `ApiError` 401/403, false otherwise.
- `buildSignInUrl(webUrl)` — the `/auth/sign-in` URL construction.
- The cookie-change predicate — "is this the session cookie being set, not removed".

## Out of scope

- Sign-out from the extension. `CorePlugin` exposes `signOut`, so it is easy to
  add later, but there is no account UI in the side panel today.
- Extracting a shared `@repo/auth` package. Web's auth all lives in
  `oss/apps/web/src/{lib,routes/auth,middleware,models}`. Worth doing eventually;
  not needed for this change.
- An in-extension email/password form. Explicitly rejected — see Design decisions.

## Verification

1. `cd oss/apps/extension && pnpm compile` (tsc) and `pnpm lint` (oxlint). Do not
   run `pnpm fmt`.
2. `pnpm test` — the new pure-helper tests.
3. `pnpm dev`, load the unpacked extension, and check the real flows:
   - **Signed out** (clear cookies for the API origin): open the side panel →
     sign-in screen, no record button reachable.
   - Click "Sign in" → web app `/auth/sign-in` opens in a tab. Sign in. The side
     panel should flip to the capture page on its own, and `RecentGuidesList`
     should populate — signing in lands you on `/dashboard`, which sets the
     active-team cookie.
   - **Signed in**: open the panel → capture page directly, no sign-in flash.
   - **Session expires mid-recording**: start recording, delete the
     `authula.session_token` cookie, click something on the page. Confirm the
     capture fails immediately with a signed-out message instead of retrying with
     backoff, and the panel returns to the sign-in screen.
4. Repeat the signed-out check in Firefox (`pnpm dev:firefox`). Firefox is
   stricter about cross-site cookies and `browser.cookies.onChanged` timing, and
   the session cookie is `SameSite=lax` / `Secure=false`.
